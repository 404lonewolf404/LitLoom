# Security Notes

The application binds to `127.0.0.1` by default and currently uses a shared local PostgreSQL research workspace. API keys are accepted through the OpenAI-compatible settings panel, a local secret file, or environment variables and are deliberately kept out of PostgreSQL, audit events, request bodies in logs, and backup manifests.

Optional account protection is enabled with `LITLOOM_AUTH_MODE=team`. On first startup, LitLoom writes a one-time administrator bootstrap token to `<LITERATURE_DATA_DIR>/bootstrap-admin-token.txt` (the default data directory is `<project>/data`). Enter that token in the first-run screen to create the owner account; the token is consumed and removed. Passwords use PBKDF2-HMAC-SHA256 with a per-password random salt. Sessions are server-side, expire after seven days of inactivity and at 30 days maximum age, and are revoked on logout, password change, or account suspension. Login attempts are throttled after eight failures in a ten-minute window. Unsafe requests require a session-bound CSRF token. Session cookies are HttpOnly and SameSite=Strict.

The optional MCP stdio adapter can use a separate local service token when team authentication is enabled. Set `LITLOOM_MCP_TOKEN_FILE` (preferred) or `LITLOOM_MCP_TOKEN`, plus `LITLOOM_MCP_USERNAME`; the server resolves that username in the current workspace before allowing a request. The token replaces only the browser CSRF step for that authenticated integration request. The member's role checks and audit actor remain active. Do not put the token in a repository, URL, MCP prompt, or shared client configuration visible to untrusted users.

The optional roles are owner, admin, researcher, reviewer, and viewer. Researchers can use the current workspace; reviewers can submit supported feedback; viewers are read-only; only owner/admin can change model and service settings, manage membership, read audit events, or download full backups. PostgreSQL currently supports the shared workspace mode only. `LITLOOM_TENANT_MODE=isolated` is rejected while PostgreSQL row-level tenant isolation is unavailable. The service still rejects non-loopback bind addresses; local accounts do not make it safe to expose the current HTTP server to a LAN or the public internet. Remote team hosting needs a separately designed HTTPS deployment, trusted proxy policy, and origin validation.

When the settings panel saves a new key, it stores it in `<LITERATURE_DATA_DIR>/model-secret.json` by default. Set `LIT_AGENT_API_KEY_FILE` to use another local JSON or plain-text file. The file is written atomically and uses restrictive permissions where the operating system supports them; protect the containing directory and do not commit it. The runtime resolves keys in this order: current process, local file, then `LIT_AGENT_API_KEY`. The settings response reports only the source and whether a key exists. Use “清除本地密钥” in the model settings panel to remove the local file.

The model configuration accepts `https` for remote providers and `http` only for loopback services. Before enabling an external provider, review its retention policy. The current AI workflow sends only the explicitly consented paper title, authors, year, venue, and abstract; local notes and PDF attachments are not uploaded.

Backups contain paper metadata, notes, audit history, a PostgreSQL dump, and local PDF attachments. Treat backup archives as sensitive research material. Store them in a protected directory and do not commit `.env`, `data/`, or backup archives to source control.

Future encrypted backup and system credential-store support must preserve the same constraints: secrets must not enter logs, exports, or model prompts without an explicit user action.
