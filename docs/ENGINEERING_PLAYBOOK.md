# LitLoom 工程流程

## 从需求到上线

```text
需求 -> 验收指标 -> 影响分析/ADR -> 领域设计 -> 实现
  -> 单元/契约/集成测试 -> 数据迁移排演 -> 发布门禁
  -> 灰度/监控 -> 复盘 -> 文档和测试固化
```

### 需求和设计

每个功能先定义输入、输出、状态和失败行为。例如“AI 初筛”必须明确：候选不自动入库、单批并发上限、结构化 JSON 校验、部分成功如何展示、重试是否幂等、刷新后如何恢复。跨领域的持久化决策记录在 `ADR.md`，API 变化同步 `openapi.yaml`。

### 实现和测试

先写纯函数和领域规则，再接数据库和 HTTP。外部模型、Tavily、学术索引使用可控 stub；真实服务只在人工验证阶段调用。长任务必须进入 `jobs` 状态机，状态至少包括 queued、running、succeeded、failed、cancelled、interrupted，并持久化进度和错误码。

测试分为四层：

- 单元测试验证解析、去重、排序、错误分类和配置校验；
- API 契约测试验证状态码、字段和 `error_code`；
- 数据库集成测试验证 PostgreSQL 迁移、约束和回滚；
- 浏览器 smoke test 验证主要路径和刷新恢复，不依赖模型额度。

### 发布和回滚

发布前执行 `scripts/verify.ps1`，确认 `scripts/doctor.ps1 --Strict` 没有配置错误、数据库备份可读、迁移在副本上成功、`/api/health` ready。发布顺序是：停止批量任务 -> 备份 -> 应用迁移 -> 启动新版本 -> 健康检查 -> 小流量验证 -> 恢复调度。

发现问题时优先关闭 canary 功能或停止调度，保留审计和任务记录；应用回滚到上一版本，数据库按迁移的 down 策略或备份恢复。任何数据恢复都要再次执行健康、完整性和论文数量核对。

## 如何读懂企业开发

“企业级”不是代码数量，而是每个变化都有边界、契约、测试、观测和回滚路径。LitLoom 选择模块化单体，是因为论文分析和检索仍共享大量本地数据与任务状态；当并发、团队隔离或部署规模达到阈值时，可沿 `providers`、`jobs` 和 HTTP 契约拆出独立 worker，而不会先承担微服务的分布式事务成本。
